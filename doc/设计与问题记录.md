- 存放位置：**项目目录之外**，例如 `D:\keys\sushivip.jks`

## 第二部分：设计决策及其理由

每条都记录了「为什么不用另一种做法」，因为那才是以后容易改错的地方。

### 2.1 代码结构

```
MainActivity.kt              容器主体：WebView 配置、权限、生命周期编排
bridge/AppBridge.kt          JS 桥接，只暴露 getDeviceId()
device/DeviceIdProvider.kt   ANDROID_ID + 本地缓存兜底
network/NetworkChecker.kt    加载前的网络前置校验
network/ConnectivityDiagnostics.kt  失败后的自助诊断
network/HostsProxyServer.kt  内置 hosts 用的本地 CONNECT 代理
web/AppWebViewClient.kt      导航控制、错误拦截、SSL 策略
web/AppWebChromeClient.kt    相机权限请求、文件选择入口
web/FileChooserDelegate.kt   拍照/相册/文件选择的完整实现
```

拆分原则：**MainActivity 只做编排，具体策略下沉到各自的类**。
WebViewClient 和 WebChromeClient 分开是因为它们承接的是两类完全不同的事件
（前者是导航与错误，后者是网页向宿主索要能力）。

### 2.2 必须 HTTPS —— 这是整个项目的地基

需求文档原本设想跑在 `http://` 上，但这与「网页内嵌扫码」**技术上互斥**。

Chromium 只在**安全上下文**（`https://` 或 localhost）下提供 `navigator.mediaDevices`。
`http://` 页面里它是 `undefined` —— 不是权限被拒，是 API 根本不存在，原生的
`onPermissionRequest` 连触发机会都没有。

受影响的不止相机：`crypto.subtle`、Service Worker、`navigator.clipboard`、
Geolocation 在 `http://` 下**全部不可用**。

**方案**：内网自建 CA 签发证书 + APK 内置该 CA 作为信任锚点
（`res/xml/network_security_config.xml` 的 `trust-anchors`）。
效果等同一张完全合法的证书，不报错、不需要绕过。

**为什么不用 `onReceivedSslError` + `proceed()`**：那等于接受任意伪造证书，
TLS 安全性归零，且不同 WebView 版本对"带证书错误的页面"是否放行相机行为不一致。
代码里 `AppWebViewClient.onReceivedSslError` **故意调用 `handler.cancel()`**，
让证书问题响亮地暴露出来，而不是静默降级。

### 2.3 「放开跨域限制」做不到

需求 3.2 提到这一条，但**原生 WebView 没有任何开关能关闭 CORS**。
`setAllowUniversalAccessFromFileURLs` 只对 `file://` 页面有效。

能做的是相邻但不同的两件事，都已实现：
- 混合内容：`MIXED_CONTENT_ALWAYS_ALLOW`
- 明文流量：`network_security_config`（证书上线后已关闭）

真正的跨域只能服务端加 `Access-Control-Allow-Origin`。
（`shouldInterceptRequest` 代理是个死路：**该 API 拿不到 POST 请求体**。）

### 2.4 JS Bridge 只暴露一个方法

`addJavascriptInterface` 注入的对象对页面内**所有框架可见，包括第三方 iframe**。
每多暴露一个方法就多一份被页面内不受控内容滥用的面。

配套的两道防线：
1. `AppWebViewClient` 只允许在 `HOST_WHITELIST` 内导航，站外链接转交系统浏览器
2. `proguard-rules.pro` 里的 keep 规则 —— **删了它 release 包会报
   `getDeviceId is not a function`，而 debug 包一切正常**，这种只在正式包
   复现的问题极难查

想区分 debug/release 包时，**不要往 AppBridge 加 `getBuildType()`** ——
UA 里已经有 `SushiVIP/1.0.0-debug` 后缀，前端改个正则就能读到
（见 `sushivip-bridge.js` 的 `container()`）。

### 2.5 targetSdk 停在 35

从 **targetSdk 36** 起，系统会在大屏设备（最小宽度 ≥ 600dp，即本项目的平板）上
**忽略 `screenOrientation` 的横屏锁定**，平板会随重力旋转，违反需求 3.1。

升级前必须先在 `<activity>` 里加兼容属性退回旧行为，否则会返工。

### 2.6 configChanges 必须声明齐全

```xml
android:configChanges="orientation|screenSize|smallestScreenSize|screenLayout|
                       keyboardHidden|keyboard|navigation|uiMode|density|fontScale"
```

不声明的话，任何配置变化（旋转、分屏、字体大小、深浅色切换）都会重建 Activity，
WebView 随之整页重载 —— **用户填到一半的表单直接丢失**。

### 2.7 三个「不写就静默失败」的配置

这类问题最难查：没有报错、没有提示、功能就是不工作。

| 配置 | 不写的后果 |
|---|---|
| `mediaPlaybackRequiresUserGesture = false` | getUserMedia 的视频流不自动播放，**扫码取景框全黑且无任何报错** |
| `onShowFileChooser`（`FileChooserDelegate`） | 网页里点上传按钮**毫无反应** |
| `filePathCallback` 必须且只能回调一次 | 漏掉的话该 `<input>` **永久失效**，之后再点也没反应 |

### 2.8 ANDROID_ID 需要兜底

`ANDROID_ID` 按「应用签名 + 用户 + 设备」派生，并非绝对可靠：

- 换签名会变（**debug 包与 release 包不同**）
- 恢复出厂、多用户、应用分身都会变
- 少数 ROM 返回 null、空串，或历史垃圾值 `9774d56d682e549c`

`DeviceIdProvider` 的处理：识别已知无效值 → 降级为随机 UUID → 落盘缓存，
保证 `getDeviceId()` 永远返回非空且在本次安装内稳定的值。

### 2.9 NetworkChecker 用 INTERNET 而不是 VALIDATED

内网 WiFi 上不了公网，用 `NET_CAPABILITY_VALIDATED` 会把它误判成"没网"，
直接阻断加载。所以只判断 `NET_CAPABILITY_INTERNET`，
真正的服务端可达性交给 WebView 的错误回调兜底。

### 2.10 错误拦截必须判 isForMainFrame

`onReceivedError` / `onReceivedHttpError` 对页面里**每一个**子资源失败都会触发。
不判断的话，主页面明明正常显示，却因为一张图片 404 就弹出错误页。

### 2.11 内置 hosts 用代理而不是直接改成 IP

见第三部分「问题二」。核心是：**代理方案保留了 SNI 和 Host 头**，
服务端虚拟主机、Cookie 作用域、重定向全不受影响；直接用 IP 则三者都会受影响。

## 第三部分：踩过的坑（完整复盘）

### 问题一：HTTP 与网页扫码不可兼得（需求评审阶段）

| | |
|---|---|
| **现象** | 需求文档同时要求「目标地址可能是 HTTP」和「网页内嵌扫码」 |
| **根因** | Chromium 只在安全上下文提供 `navigator.mediaDevices`，两条需求技术上互斥 |
| **解决** | 内网自建 CA 签发证书（SAN 同时写 DNS 名和 IP）+ APK 内置该 CA |
| **教训** | 这类冲突要在**动手前**发现。如果先写完代码再发现，服务端改造要重排期 |

工具：[`tools/gen-intranet-cert.sh`](../tools/gen-intranet-cert.sh)

关键点：**Chromium 早已不读 CN 字段，只认 SAN**，缺 SAN 会报
`ERR_CERT_COMMON_NAME_INVALID`。

### 问题二：域名解析失败 `ERROR_HOST_LOOKUP (-2)` ⭐ 最耗时

| | |
|---|---|
| **现象** | App 报「无法解析服务器地址」，**但同一台平板的浏览器能正常打开** |
| **误导性** | 这个组合极具迷惑性 —— 两者用的是同一个系统 resolver，看起来不可能 |

**排查过程与结论**：

```
adb shell ping -c 3 lms.sushisom.net
→ ping: unknown host                    ← 系统层就解析不了，与 App 无关

adb shell ping -c 3 192.168.2.32
→ 0% packet loss                        ← 网络本身完全正常

adb shell "dumpsys connectivity | grep -i dns"
→ DnsAddresses: [ /fe80::124%wlan0, /192.168.2.31, /192.168.2.1 ]
                 ^^^^^^^^^^^^^^^^^ 根因在这里
```

**根因**：平板配了三个 DNS，**排在第一位的是 IPv6 链路本地地址**
（路由器通过 IPv6 路由通告 RA 下发）。而域名重写记录在 `192.168.2.31` 上。

平板先问 `fe80::124`，那台不认识这个域名 → 返回 **NXDOMAIN**。
这是**权威否定答复**（"确实不存在"），不是失败 ——
系统解析器据此直接放弃，**根本不会再去问后面持有记录的 192.168.2.31**。

Chrome 能打开，是因为 Chromium 自带的异步解析器会跳过链路本地 IPv6 DNS，
直接问 `192.168.2.31`；而 WebView 走系统解析器，老实按顺序问，第一个就被否掉了。

**解决（两层，都做了）**：

1. **网络侧根治**：路由器关闭 IPv6 → `fe80::124` 从列表消失；
   再把 DHCP 的辅 DNS（`192.168.2.1`，同样会返回 NXDOMAIN）清空，
   只留 `192.168.2.31`，消除对查询顺序的依赖
2. **App 侧免疫**：`HostsProxyServer` —— 应用内起一个只监听回环的 CONNECT 代理，
   WebView 通过 `ProxyController.setProxyOverride()` 走它，把域名解析这一步
   接管到应用自己进程内

**为什么第 2 层要用代理而不是直接把地址改成 IP**：

| | 改成 IP | 内置 hosts（代理） |
|---|---|---|
| SNI / Host 头 | 变成 IP，nginx 虚拟主机可能命中错站点 | **仍是域名** ✅ |
| Cookie 作用域 | 绑到 IP，带 `Domain=` 的 Cookie 失效 | **不受影响** ✅ |
| 服务端重定向到域名 | 会跳出去然后失败 | **不受影响** ✅ |
| 证书 | 要求 SAN 含 IP | 按域名校验即可 ✅ |

**为什么不能直接给 WebView 写 hosts**：Android 没有向 WebView 暴露任何覆盖 DNS 的
公开 API。Chromium 有 `--host-resolver-rules`，但只能通过命令行文件注入，
且仅 debuggable 设备可用，应用无法给自己设置。
突破口在代理协议：HTTPS 走代理时客户端发的是 `CONNECT 域名:443`，
**域名解析由代理端负责** —— 把代理放进自己进程，这一步就归自己管了。

**为什么代理要带 DNS 回退**：映射是编译期写死的，服务器一旦换 IP，
映射本身就成了错误答案，反而把应用堵死。所以先按映射连（3 秒超时），
连不上再退回系统解析。

### 问题三：证书未替换 `SSL_UNTRUSTED (-1000)`

| | |
|---|---|
| **现象** | DNS 修好后错误码从 -2 变成 -1000，「HTTPS 证书不受信任」 |
| **根因** | `res/raw/intranet_ca.crt` 还是工程初始化时放的**占位证书** |
| **解决** | 换成实际签发服务器证书的根 CA |

**这是刻意设计的失败模式**。占位证书的 CN 写着
`PLACEHOLDER - REPLACE WITH REAL INTRANET CA`，私钥在生成时就已销毁，
任何人都无法用它签发。它的作用是让「忘记替换」这个错误**明确报出来**，
而不是静默降级成不安全连接。

**验证方法**（两者的 CN 必须一字不差）：

```bash
# APK 内置的 CA
openssl x509 -in app/src/main/res/raw/intranet_ca.crt -noout -subject
→ subject=CN = Intranet Root CA, O = Intranet

# 服务器证书是谁签的
openssl s_client -connect 127.0.0.1:443 -servername lms.sushisom.net </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer
→ issuer=CN=Intranet Root CA, O=Intranet
```

**教训**：这一步在部署手册的阶段二，但因为一直在救 DNS 的火被跳过了。
**部署手册的阶段顺序是有依赖关系的，跳步会在后面加倍还回来。**

### 问题四：排查过程中的环境类小坑

这些单独看都很小，但排查时会打断节奏，记下来省得下次再撞。

| 坑 | 现象 | 处理 |
|---|---|---|
| PowerShell vs cmd | 提示符是 `C:\...>` 是 cmd，`PS C:\...>` 才是 PowerShell，两者语法不通用 | 看提示符判断 |
| 粘贴到注释行 | `# Windows PowerShell（当前窗口有效）` 被当成命令执行报错 | `#` 开头的是注释，不要粘 |
| adb 不在 PATH | `adb 不是内部或外部命令` | 直接 `cd` 到 platform-tools 目录敲，或 PowerShell 里 `$env:Path += ";$env:LOCALAPPDATA\Android\Sdk\platform-tools"` |
| Windows 没有 git / grep / chmod | 一堆 `无法将...识别为 cmdlet` | 用 Android Studio 的 `Git` 菜单；过滤用 `findstr`；或把过滤放到设备上做（`adb shell "... \| grep ..."`，设备上的 toybox 有 grep） |
| AS 里找不到 `res/raw` | Android 视图下需要展开 `res` 节点 | 展开即可；或 `Ctrl+Shift+N` 按文件名搜；或把面板从 `Android` 切到 `Project` 视图 |
| logcat 抓不到有用内容 | `adb logcat -d -t 300` 抓的是全系统最近 300 行，早被刷掉了 | 先 `adb logcat -c` 清空 → 复现 → 再 `adb logcat -d > logcat.txt` |

### 问题五：排查中我自己犯的三个判断错误

记下来是因为**这些是诊断时容易踩的思维陷阱**，不是简单笔误。

| 错误判断 | 实际情况 | 陷阱在哪 |
|---|---|---|
| grep 关键词写成 `Dns addresses`（带空格） | 实际字段是 `DnsAddresses`（无空格），导致第一次采集**什么都没匹配到**，白跑一轮 | 凭印象写字段名。应该先用宽松的 `grep -i dns` 看全貌，再收窄 |
| 看 `ip route` 只有一条 `192.168.2.0/24`、没有默认路由，判断是「静态 IP」 | `adb shell ip route` **只显示主路由表**，Android 的每网络路由在独立表里。完整的 `LinkProperties` 显示默认路由 `0.0.0.0/0 -> 192.168.2.1` 一直都在，DHCP 完全正常 | 用了一个视图不完整的命令下结论。Android 上看网络状态要用 `dumpsys connectivity` |
| 说私人 DNS 设成「自动」会走公共 DoT、绕过内网 DNS，要求逐台平板关闭 | 「自动」是**机会性 DoT**，用的仍是网络下发的那台 DNS 服务器，不会绕过路由器。只有填写具体主机名的**严格模式**才会绕过 | 把三种模式混为一谈，凭空多加了一个部署步骤 |

**通用教训**：`ping` 一条命令就能把「系统层解析不了」和「仅 App 解析不了」分开，
应该**在所有猜测之前先跑它**。前面几轮的推测（启动竞态、WiFi 代理、
默认网络切到蜂窝）都是在缺这个数据点的情况下发散出来的。

## 第四部分：故障速查

| 错误码 | 文案 | 根因 | 处理 |
|---|---|---|---|
| `-2` | 无法解析服务器地址 | DNS 问题 | 先 `adb shell ping -c 3 <域名>`；再看 `dumpsys connectivity \| grep -i dns` 的服务器列表 |
| `-1000` | HTTPS 证书不受信任 | 内置 CA 与服务器证书的签发者不一致 | 对比 APK 的 CA subject 与服务器证书 issuer |
| `-1000` | HTTPS 证书域名不匹配 | 服务器证书 SAN 里没有当前访问的域名/IP | `openssl ... -ext subjectAltName` 确认 |
| `-6` | 无法连接到服务器 | 服务未启动 / 端口未放行 | 服务器上 `ss -lntp \| grep 443`，检查 ufw 与宝塔安全 |
| `-8` | 连接服务器超时 | 网络不通 | `ping` 服务器 IP |
| HTTP 404/500 | 服务器返回 HTTP xxx | 服务端问题 | 看 nginx 日志 |

**App 内置自助诊断**：加载失败时，错误页下方会自动显示三项探测结果
（域名解析 / 解析地址是否可达 / IP 直连是否可达）和结论，**不用连电脑**。
实现见 `network/ConnectivityDiagnostics.kt`。

**看日志**：

```
adb logcat -s MainActivity AppWebViewClient AppWebChromeClient FileChooserDelegate Diagnostics HostsProxy
```


## 第五部分：变更清单（以后要改什么，看这里）

| 要改什么 | 改哪里 | 要不要重新打包 |
|---|---|---|
| 目标地址 | `app/build.gradle.kts` 的 `baseUrl` 默认值，或 `-PbaseUrl=` | 要 |
| 服务器换 IP | `hostsOverride` 与 `FALLBACK_IP` | 要（但代理有 DNS 回退，DNS 正常时不改也能用） |
| 白名单加域名 | `HOST_WHITELIST` | 要 |
| 横屏方向反了 | `AndroidManifest.xml`：`landscape` ↔ `reverseLandscape` | 要（代码不用动） |
| 加载页底色 | `res/values/colors.xml` 的 `app_background` | 要 |
| 换 logo | `cp 新图.png doc/logo.png && python3 tools/gen_launcher_icons.py doc/logo.png` | 要 |
| 服务器证书续期 | 用**同一个 `ca.key`** 重签 `server.crt`，只更新宝塔 | **不用** ✅ |
| 根 CA 续期（10 年后） | 重新生成 CA → 更新服务器证书 → 替换 `res/raw/intranet_ca.crt` | 要，且全部平板要升级 |
| 关掉内置 hosts | `-PhostsOverride=` | 要 |

> 用内部 CA 签发服务器证书的最大价值就在倒数第三行：
> **服务器证书随时可换，只要 CA 不变，APK 就不用重新分发。**
